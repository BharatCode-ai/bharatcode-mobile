# Internal-test build preparation (no store uploads)

Allowed destinations are **Google Play INTERNAL** and **Apple TestFlight only**.
Never publish/promote to production, open/closed Play tracks, or a public App Store
release. This workflow does not contact either store, make a GitHub release,
generate signing keys, register apps, or change the default branch.

## Run manually

`.github/workflows/internal-build.yml` is a build-only workflow. All heavy npm,
Gradle, CocoaPods and Xcode work runs on hosted runners. Do not install
node_modules or run native builds in the disk-constrained local WSL checkout.

```sh
gh workflow run internal-build.yml --repo BharatCode-ai/bharatcode-mobile \
  --ref prep/internal-test-builds-20261118 \
  -f platform=both -f build_number=1 -f android_signing=unsigned

# Only after approved signing material is provisioned:
gh workflow run internal-build.yml --repo BharatCode-ai/bharatcode-mobile \
  --ref prep/internal-test-builds-20261118 \
  -f platform=android -f build_number=1 -f android_signing=upload-key
```

New branch-only workflows may require a first run before GitHub permits manual
dispatch. If needed, a temporary bootstrap trigger restricted to the preparation
branch may validate unsigned builds; remove it before final handoff. Do not merge
to main merely to register the workflow. Record exact commits and runs separately.

`source` runs mobile tests, typecheck/lint, security regressions, Expo
compatibility, resolved identity checks, and negative build-number checks before
native jobs. Existing source CI also checks the Desktop connector and helpers.
The native jobs run independently so one platform failure doesn't cancel the other.

The separate `security` job audits the lockfile and retains its JSON report. An
audit failure **keeps the workflow red and blocks upload-key signing**. Only
unsigned diagnostic compilation may continue; its metadata records the failed
audit and it cannot be uploaded to a store. This is not an audit waiver, and the
existing Source checks audit remains unchanged.

Expo's live compatibility recommendation is also a separate hard gate for signing;
its report remains an artifact and a failed `compatibility` job. Unsigned builds
can diagnose the requested, unchanged source even when the live recommendations
have advanced. Their metadata explicitly records this failure as well.

## Android signing contract (account-independent)

Use GitHub environment **`mobile-internal`** for the Android job. An authorized
owner supplies these exact environment secrets, never in logs, chat, source, or
artifacts:

| Environment secret | Contents |
| --- | --- |
| `ANDROID_KEYSTORE_BASE64` | Base64 of the approved upload keystore |
| `ANDROID_KEYSTORE_PASSWORD` | Keystore password |
| `ANDROID_KEY_ALIAS` | Upload private-key alias (not `androiddebugkey`) |
| `ANDROID_KEY_PASSWORD` | Private-key password |

Also set environment **variable** `ANDROID_UPLOAD_CERT_SHA256` to the approved
certificate's SHA-256 fingerprint (64 hex digits, optionally colon-separated).
This fingerprint is public certificate metadata, not a secret. Restrict the
environment to reviewed build refs and configure required reviewers as appropriate.
The branch workflow can build an upload-key AAB before a Play account is chosen;
there is no developer-account ID, service-account key, Play API token, or listing
creation in this configuration. Key generation and secure backup are the owner's
separate, explicitly authorized responsibility. Never rotate an existing app's
key or create a replacement key to fix a signing error.

Unsigned mode forcibly clears Expo's generated debug-signing fallback. Signed mode
requires all four secrets and the expected fingerprint; there is no fallback.
Only prerequisite and compile steps receive key secrets. The key is decoded with restrictive
permissions under runner temp, checked against its expected certificate, and removed
in an always-run cleanup step. Android Release must be non-debuggable. The final
AAB must contain arm64 libraries and embedded JS; signed AABs must pass jarsigner
verification and match the approved fingerprint. No APK is substituted for an AAB.

## Artifacts and limits

Artifacts are retained for seven days and include `build-metadata.json`,
`SHA256SUMS`, and `READ-ME-FIRST.txt`. They record the exact source commit, run,
attempt, app identity/version, signing state, and binary checksum.

- **Unsigned Android:** `BharatCode-UNSIGNED-NOT-UPLOADABLE.aab`.
  Release compilation evidence only; not a debug build or Play upload candidate.
- **Signed Android:** `BharatCode-UPLOAD-KEY-PLAY-INTERNAL-CANDIDATE.aab`.
  Cryptographically checked upload-key artifact, not a claim that Play will accept
  it. Account/listing/key registration, metadata, and final acceptance remain gates.
- **iOS:** `BharatCode-UNSIGNED-NOT-UPLOADABLE.xcarchive.tar.gz`.
  Real iPhoneOS Release archive using Xcode 26.6, not a simulator artifact.
  Code signing/provisioning is disabled; no IPA export or TestFlight upload.

Only allowlisted output files are uploaded, not keystores, Pods, native build
directories, raw environments, or provisioning profiles. Public-repository Actions
artifacts are not a private distribution channel; do not embed credentials or
customer data in builds. The AAB/unsigned archive alone does not certify a working
native installation. Do not uninstall or clear an existing app to bypass signing.

## Exact remaining release prerequisites

**Dependency security:** the first November 18 hosted run against the unchanged
lockfile reported 78 findings (11 moderate, 67 high), including the picomatch ReDoS
advisory GHSA-fc5q-39xc-vjpf and inherited tooling dependents. Mobile tests passed.
Resolve and review the locked build-tool dependency advisories before a signed
candidate can be produced. Do not use `npm audit fix --force` (its proposed Expo
downgrade is outside this build-preparation task), or bypass the audit gate.
The [picomatch advisory](https://github.com/advisories/GHSA-fc5q-39xc-vjpf), updated
November 17, lists no patched release. A reviewed remediation or separately
approved security decision is required; no exception is implemented here.

**Expo compatibility:** the November 18 live check recommends Expo ~58.0.26,
React Native 0.88.1, and matching patches for 13 other packages. The pinned source
remains unchanged and is not represented as passing that check. Updating runtime
dependencies and repeating acceptance needs separate authorization/review.

**Android signing:** the four environment secrets and certificate fingerprint
above; validate a successful signed build before requesting Play upload.

**Google Play:** publishing-account choice and access, a BharatCode app record with
the exact package ID, Play App Signing/upload-certificate registration, confirmation
that versionCode 1 is unused, required store declarations, internal tester list,
and authorized manual INTERNAL-track upload. No API token is needed for a browser
upload. The publishing account has not been selected/verified for this app, and no
matching listing is verified. This workflow assumes no specific developer account.

**Apple signing:** access to the correct Apple Developer Program team; an App ID
for `ai.bharatcode.bharatcodeMobile`; an approved Apple Distribution certificate
with private key (password-protected P12) and matching App Store provisioning
profile; the real Team ID; a matching App Store Connect app record/numeric Apple
ID; an unused build number. None is invented here. Apple access was blocked by an
embedded 502 on November 18; signing resources and membership remain unverified.
No signed iOS CI path is configured until these resources can be inspected safely.

**TestFlight delivery:** App Store Connect access/role sufficient for build upload
and internal tester management (or separately authorized API credentials), signed
archive/export, required export-compliance metadata, and internal tester group.
No external TestFlight/public App Store submission is authorized by this workflow.

**Final native acceptance:** test the exact signed store-delivered build on physical
Android/iOS: QR scan and matching-code approval, conversation/send/stream, Stop,
questions/permissions, files/diffs, offline drafts/restart/reconnect, and revocation.
The October 28 physical camera QA was a separate diagnostic APK from different
source; it does not certify the new AAB or iOS archive. See
[the pairing verification](verification/pairing-fixes-2026-10-28.md).
